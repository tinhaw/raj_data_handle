# 提现订单 Excel 导出字段映射核对表

本表参照[充值订单 Excel 导出字段映射核对表](充值订单字段对照表.md)编写，供确认提现订单页的本地缓存、明细展示和渠道汇总口径。提现订单导出 Excel 是主数据；评分审核 API 或 Excel 只能按案件号补充已存在的提现订单。页面查询只读取本地缓存，不会在用户打开或翻页时请求远端。

## 1. 刷新与安全边界

- 每个盘口按其业务时区导出一个完整自然日；原始 Excel 仅在内存中解析，成功后立即丢弃，不保存文件、完整响应或未白名单列。
- 自动任务每日业务时区 `00:05:01` 运行，默认导出前一天 `00:00:00` 至 `23:59:59`；系统配置也可改为一次性的指定日期，成功后不在次日重复执行。
- 手动刷新可选前天、昨天、今天，默认昨天，范围同样是所选自然日的完整业务时区窗口。
- 全部白名单行校验、状态识别和去重成功后，才写入或覆盖该盘口该日期的本地缓存；任何解析、认证或状态映射错误都保留原有缓存。
- 订单以 `source_id + remote_order_id` 去重；同一导出中重复主键只保留最终一行，并记录导出行数、导入数和重复数。

### 明确禁止读取、缓存和导出的列

即使远端 Excel 含有下列字段，解析器也不读取其单元格，数据库、日志、页面 API、CSV/Excel 导出均不得出现：

- 银行卡号、银行卡账户、收款人姓名；
- 手机号、银行名称、银行代码、IFSC；
- 失败原因、备注等自由文本原因；
- IP、设备信息、完整远端响应或完整 Excel 原文件；
- 任何未列入上表安全白名单的列。

## 3. 评分审核 API / Excel 补充字段与融合规则

评分审核 API 的基础地址和 API Key 必须在“盘口配置”中按 `source_id` 单独维护；它们与 RajWin / RajLuck 后台订单地址、账号、密码和 TOTP 相互独立。Key 仅以加密形式保存在服务端，前端不会取得 Key 或完整远端响应。每次提现订单刷新成功后，只有该盘口已配置评分审核 API 且连接测试状态为“通过”时，系统才会按同一创建时间范围通过 `GET /external/v1/scoring-reviews/reviewed-cases/export` 下载评分审核 Excel，并用与人工导入相同的严格白名单解析器同步评分补充数据；未配置或测试未通过时，提现订单仍会正常刷新，但不会请求评分审核接口。Excel（例如 `scoring_reviewed_cases_*.xlsx`）保留为人工备用导入方式。

两种评分数据来源都不是第二份提现订单主表，只能在**同一盘口**内按下列键做左连接：

```text
评分审核 Excel.案件号 -> 提现订单 Excel.主键 -> source_id + remote_order_id
```

- 提现订单 Excel 永远是主数据：评分表中找不到的主订单仍正常展示；评分表中找不到提现主键的行只计入导入结果的“未匹配”，不创建订单、不进入明细、渠道汇总或操作人员汇总。
- 评分表只刷新评分补充字段，不会覆盖提现主表的 `uid`、金额、渠道、提现时间、状态、审核人或任一提现订单字段。
- API 同步会先在内存下载选定时间范围的一份 Excel，再以与人工导入相同的严格白名单校验后原子写入本地评分补充缓存；工作簿压缩后最大 32 MiB、解压后最大 128 MiB、最多 100,000 行。同步不会保存原始工作簿、姓名、银行卡、远端请求数据、失败原因或未知新增字段。
- 导入时只在内存中解析评分 `.xlsx`，不保存原始工作簿、完整行或未白名单字段；重复导入同一案件会原位覆盖该案件已有的评分补充值。
- 评分补充缓存和提现主缓存均按 `source_id` 隔离；RajWin 与 RajLuck 不会互相匹配或复用数据。

| 评分审核 Excel 列 | 关联/本地字段 | 明细展示 | 使用说明 |
| --- | --- | --- | --- |
| 案件号 | `withdraw_order_id`；关联提现主表 `remote_order_id` | 间接引用 | 必填；只作为同盘口的关联键，不展示为另一份订单 ID。 |

评分审核操作人汇总以提现主订单创建时间筛选，并仍以主表审核人分组。没有评分补充行或评分值为空/非数值的主订单记为“未进入评分”，且按既定口径同时计入 `≤30 分`；因此它是 `≤30 分` 的子集，不能额外加入总数。

## 4. 页面字段与分组

页面采用四个独立标签：`提现订单明细`、`支付渠道汇总`、`操作人员汇总`、`评分审核汇总`。前两者按创建时间和支付通道分析，操作人员汇总按审核人和状态统计，评分审核汇总按主订单审核人和评分区间统计；四者都只读本地缓存。

渠道汇总的一行固定按下列键分组：

```text
source_id + 创建日期（盘口业务时区） + pay_channel
```

`pay_channel_name` 是显示名，缺失时使用渠道代码。相同渠道代码不能因显示名变化拆为多行。

## 5. 渠道汇总指标口径

分母均限定在**同一盘口、同一创建日期（盘口业务时区）**的本地缓存订单；所有数量均按去重后的 `remote_order_id` 计算，所有金额均由服务端以精确十进制求和。分母为零时显示 `—`，不显示 `0%`。

| 汇总列 | 依赖字段 | 计算公式 |
| --- | --- | --- |
| 日期 | 创建时间 | 创建时间换算到盘口业务时区后的自然日。 |
| 支付渠道名称 | 支付通道名称、支付通道 | 显示 `pay_channel_name`，缺失时显示 `pay_channel`。 |
| 提款总订单数 | 主键 | 当前渠道所有去重订单数。 |
| 代付成功订单数 | 主键、状态 | 当前渠道状态为“代付成功”的去重订单数。 |
| 代付成功金额 | 到账金额、状态 | `sum(real_amount)`，仅状态为“代付成功”。 |
| 提款总手续费 | 提现手续费、状态 | `sum(fee)`，仅状态为“代付成功”。 |
| 代付失败数 | 主键、状态 | 当前渠道状态为“代付失败”的去重订单数。 |
| 已提交代付数 | 主键、状态 | 当前渠道状态为“已提交代付”的去重订单数。 |
| 审核拒绝数（补充） | 主键、状态 | 当前渠道状态为“审核拒绝”的去重订单数；单列展示，避免与代付失败混淆。 |
| 渠道代付成功订单量占比 | 主键、状态、支付通道 | 当前渠道代付成功订单数 ÷ 当天全部渠道代付成功订单数。 |
| 渠道代付成功金额占比 | 到账金额、状态、支付通道 | 当前渠道代付成功金额 ÷ 当天全部渠道代付成功金额。 |
| 卡单率 | 主键、状态 | 当前渠道已提交代付数 ÷ 当前渠道提款总订单数。 |
| 代付成功率（补充） | 主键、状态 | 当前渠道代付成功订单数 ÷ 当前渠道提款总订单数。 |

图表、指标卡、渠道表和导出必须复用同一个服务端聚合结果，前端不得重新计算上述指标。页面悬停图表时可显示渠道名称和值；圆弧引线标签仅显示名称，避免金额文字挤占图面。

## 6. 已确认与待人工确认项

已确认：

1. “修改时间”即提现订单的完成时间，页面固定显示为“完成时间”。
2. 各盘口 `withdraw_status` 字典完整覆盖导出中的全部状态文案；导入时仍会校验同一文案不会歧义对应多个代码。
3. 评分审核 Excel 按 `案件号 -> 主键` 融合，提现订单 Excel 是唯一主数据；评分 Excel 无匹配主键时不补建订单。
4. 评分审核远端 API 按盘口独立配置，使用 `/api` 基础地址及具有 `scoring.reviewed-cases:read` 权限的独立 API Key；不得复用订单后台登录凭据。

仍待人工确认：

1. 远端 Excel 列名与上表完全一致，尤其是“主键”“支付通道”“到账金额”“修改时间”。
2. 是否需要在明细页增加“审核拒绝数”和“代付成功率”以外的业务指标；未确认前不增加敏感字段。

# richer 创建兑换码组：重复充值门槛诊断

日期：2026-11-01。证据范围为用户截图、本地源码和内存复现；未访问生产环境、账号预设、请求日志或远端业务接口。

## 结论与边界

- case：截图中四个盘口创建均返回“充值门槛不能重复”。
- failure type：tool_or_backend，用户人群配置与旧充值档位唯一性约束不一致；是否属于新回归尚无版本证据。
- audit depth：full，检查到本地活动创建前置校验；该校验失败后停止，无需实际发起创建或发布验证。
- first broken link：兼容服务 `RedemptionService.replaceTiers` 仅以 `minDepositAmount` 判断档位重复，不考虑用户类型及标签。
- node containment：not_applicable；本项目此处没有 LLM 节点。

截图中“全部用户”和“(5001)游戏总局数0”是最可能冲突的两档。全部用户门槛固定为 0；新增标签档位初始门槛也是 0，游戏局数标签不能被充值金额解析器识别，会沿用原门槛。实际 richer 预设的隐藏值尚未读取，因此该档位归因是有源码和复现支持的推断。

## 影响和修复方向

- root cause：界面已按人群定义奖励档位，后台和数据库仍要求同活动内充值门槛唯一；预设保存与创建校验也不一致。
- risk / impact scope：所有使用重复门槛、不同人群的兑换码组均可能被拒绝，和登录用户名没有直接关联；四个盘口各自的真实请求尚未核对。
- fix direction：先明确按人群区分档位的契约，再协调兼容服务、数据库唯一约束及前端提示；不能只删除 Java 校验，也不能给隐藏门槛随意添加差值绕过。
- 临时操作：仅当业务允许取消其中一种人群时，移除对应档位并逐盘口核对；这会改变发放人群，不能视作等价修复。
- rollback strategy：本轮无业务代码、生产数据或结构变更；未来若修复放开重复门槛，产生新数据后无法直接恢复旧唯一约束，应优先回退入口能力并保留数据。
- feature flag / canary：若实施，建议先仅开放创建入口能力给测试账号，旧数据仍可读取；生产结构变更须单独授权。
- tests to run：error_boundary（重复输入明确报错）、draft_crud（相同门槛不同人群创建）、persistence（档位顺序和人群绑定）、query_readback（历史读取）、跨类型/跨盘口预设回归；使用隔离本地数据库和远端替身，不创建真实远端兑换码。
- remaining uncertainty：richer 当前实际预设门槛、四盘口请求内容、生产版本和失败事务日志尚未读取；本次没有宣称修复或线上验证完成。

回归规则：任何新增的非充值标签人群或全部用户组合，都必须覆盖“门槛相同而人群不同”的创建契约，不能只验证预设可保存或前端可展示。

## 用户授权后的本地修复

用户随后明确要求解除充值门槛重复限制。以上“本轮无业务代码变更”为最初诊断阶段的记录；当前本地修复已完成，尚未部署或执行生产迁移。

修复前检查：

- main goal：允许不同档位使用相同充值门槛，包括截图中的全部用户与游戏局数标签。
- acceptance points：独立保存档位 ID、金额范围及标签绑定，创建批次后可从新请求或新会话读回；旧记录完整保留；存在重复数据时拒绝有损降级。
- impact scope：Java 兼容活动创建、Python 本地活动创建及预设匹配、两张档位表的唯一约束。分类为 shared_layer，涉及上述服务及持久化层，非 LLM 节点。
- risk level：中，包含结构迁移；实际远端创建与发布未验证。
- rollback strategy：先关闭相关创建和计划配置入口、停止相关执行，再决定应用回退或向前修复；新增重复档位后保留新结构，不删记录、不改门槛以强行降级。
- regression plan：draft_crud、persistence、query_readback、error_boundary；覆盖三种兑换码类型、人群绑定、跨日批次、预设歧义拒绝及迁移升降级。

实施内容：

1. 移除 Java 与 Python 的重复门槛拒绝逻辑；保留非负金额、金额上下限、标签和权限校验。
2. 新增 Alembic `20261101_0052`，仅删除两张档位表的门槛唯一约束；不改历史迁移。降级先检查两张表，任何一张存在重复档位都拒绝恢复旧约束。
3. 新增仅用于独立测试的 Flyway V29，按列集合定位 V5 的自动命名约束；生产继续禁用 Flyway，由本项目 Alembic 负责 DDL。
4. 下游审计发现 Python 批量预设匹配原本以“名称或门槛匹配到的第一项”为准。放开门槛唯一性后，新增测试确认它会将不同人群误绑定到第一档。此为同一修复范围内被新能力触发的 `business_regression` 风险，首个断点在 `configure_erp_redemption_task_remote_plans` 的预设选择处。改为优先按名称唯一匹配，兼容仅有一个候选项的门槛回退；多个候选项明确报错，配置任何子任务前完成全部匹配检查。
5. Java 生成与导出链路使用档位 ID、配置 ID 关联记录；门槛相同不合并任务或导出列。现有备注和列标题可能相同，本次未改其格式。

验证结果（本地）：

- `pytest -q`：362 项全部通过，其中包含 0 与正数门槛重复、同门槛不同人群预设匹配、歧义拒绝、新会话读回及迁移保留历史数据等回归。
- Java `mvn -q test`：131 项通过，日充值、近七天、代理类型均创建并读回同门槛的两档，保留不同标签和 5～7 / 5～17 的奖励范围；远端客户端使用 mock。
- `node --test tests/redemption-*.test.mjs`：36 项通过。
- 相关 Python 文件及 `deploy tests` 的 Ruff 检查、发布脚本 Shell 语法检查、`git diff --check` 通过。
- 数据库验证使用隔离 SQLite 与 H2；未连接 RDS，也未对 PostgreSQL 运行本次迁移。

生产实施前须按 AGENTS.md 明确目标环境为本项目 `data_handle`、可恢复的备份与回退方案、风险和执行窗口。暂停兑换码相关写入口及执行，在窗口内通过本项目发布脚本先独立迁移再更新应用，全部服务完成更新后才恢复入口，避免旧 Python 预设匹配逻辑处理新重复档位。首次验收可限测试账号；本次未引入功能开关，也未发起线上创建、发布、同步标签或连接检测。

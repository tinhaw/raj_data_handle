## 2. 目标结构

```text
apps/web
  /erp/*                    原 ERP 页面进入当前 AppShell

/api/*                     当前 FastAPI：分析、统一身份、统一远端账号
/erp-api/api/v1/*          ERP 兼容 API：保持线上 ERP 请求/响应契约

data_handle
  当前用户/会话            唯一身份来源
  SourceConfig             唯一盘口来源
  RemoteAccount            唯一远端账号与密文凭据来源
  ERP 业务表               台账、导入、兑换码、审计
```

高保真优先于技术栈统一。ERP 核心可以先作为仓库内独立兼容服务保留原 Spring
业务实现；旧 ERP 的登录、用户密码、盘口凭据和会话表不得随之启用。兼容服务必须读取当前身份、权限和统一远端账号适配层。

## 3. 执行阶段

### P0：线上黄金基线

- 固定 10 个页面、所有弹窗、表格列、按钮条件、默认值和提示语。
- 固定旧 API 的路径、请求/响应、错误码、下载文件和状态机。
- 保存桌面端视觉基线，并建立页面、API、权限、数据和导出的逐项矩阵。
- 所有线上巡检保持只读，不提交表单，不触发连接检测、标签同步或兑换码远端操作。

### P1：统一身份与兼容网关

- `/erp-api` 使用当前 Session Cookie 和用户表，不保留第二套登录。
- 内部只读身份契约为 `/api/v1/erp/access/compatibility-session`，数据归属和权限映射见
  [erp-compatibility-boundary.md](./erp-compatibility-boundary.md)。
- 将原 ERP 角色和投放公司范围绑定到当前用户 ID。
- 建立旧 API 错误包装与当前权限拒绝之间的兼容层。
- Nginx 只把 `/erp-api` 转发给 ERP 兼容服务，分析 API 路由保持不变。

### P2：原样前端迁入

- 从旧 ERP 迁入页面、组件、样式、工具和 API 类型。
- 去除旧 AppLayout/LoginPage，接入当前 AppShell 和 `/erp/*` 路由。
- API 基地址改为 `/erp-api/api/v1`，其余请求和响应适配尽量保持不变。
- 旧页面先通过管理员影子入口验收，验收前不替换生产导航。

当前进度：10 个线上同源页面保留在 `/erp-preview/*` 影子路由；工作台、投放公司、
台账、导入、兑换码、报表和审计的正式路由已经切换为同源页面模块。用户、系统设置
和远端账号继续使用当前主系统页面，这是统一身份和统一远端账号的有意融合点。

### P3：本地 ERP 业务兼容

- 按投放公司/投放线、台账/锁账、导入、报表、审计顺序接入。
- 将原 Flyway 结构转换为 Alembic，并与现有 ERP 表逐字段映射。
- 同一输入同时运行旧服务与兼容服务，比较 API、金额、状态及 Excel。

完成结果：0035 已定义 `erp_compatibility_id_maps`，为线上 Long ID 与当前
UUID/字符串 ID 建立稳定 crosswalk。0036 已按线上字段定义投放公司、投放线、台账、
锁账、导入和审计兼容表，并把现有本地 ERP 数据转换到兼容结构。全新 SQLite 已完成
0001→0037 升级，带样例数据的 0035→0036 转换也已通过；生产 `data_handle` 已完成
0035–0037。线上历史数字 ID 将原值保留；当前项目转换记录使用 `9_000_000_000_000`
以上的保留区，防止后续历史导入发生主键冲突。

### P4：远端账号和兑换码兼容

- 旧 `market` 映射到 `SourceConfig`，旧连接映射到 `RemoteAccount`。
- 登录、TOTP、会话、标签和档位预设只经统一账号服务读取。
- 恢复线上任务组、盘口子任务、单项创建、发布、取消、下载和恢复状态机。
- 每个远端操作继续同时要求账号能力与一次性执行授权；代码迁入不代表生产执行授权。

当前进度：0037 已提供线上字段和 Long ID 兼容的活动、档位、任务组、批次和单项表，
并把当前活动/任务/远端计划数据投影到线上状态。Spring 本地状态机读取统一账号注册表，
账号选择必须具备 `ERP_REDEMPTION_CREATE`，标签只读统一快照。融合模式下旧凭据客户端
被硬阻断；远端操作协议和 runner 已迁入，但本轮没有公开执行入口，也没有发出远端请求。

### P5：数据迁移与切换

- 在隔离的 `data_handle` 快照副本上至少完成一次全量迁移演练。
- 核对行数、金额汇总、任务/子任务关系、远端标识、文件和审计时间线。
- 生产切换必须另行确认旧 ERP 停写、最终增量、备份、回退负责人和窗口。
- 回退只切回旧 ERP 路由，不影响数据分析模块；不得访问 `review_recheck`。

当前进度：已实现只允许 `snapshot` / `rehearsal` 数据库的历史导入工具，并完成合成样例与
2026-08-27 旧 ERP 生产一致性备份到全新 0037 PostgreSQL 隔离目标的两次全链路演练。
真实演练覆盖统一用户、盘口/账号映射、Long ID、金额、任务关系、标签/档位、逐行摘要、
历史软引用分类和 PostgreSQL sequence 同步；12 张业务表数量/摘要一致，硬关联孤儿为 0。
稳定业务键目录解析器会把旧用户名、盘口代码和远端登录名解析成明确 ID；缺失的兑换账号
只会在隔离库创建为禁用、无凭据、无能力授权的统一账号占位，不会复用历史分析默认账号。

真实 `data_handle` 0034 生产备份的隔离克隆演练也已完成：0035–0037 一次升级成功，
原 48 张表行数在 schema 阶段全部不变；历史导入后只改变 7 张预期的 ERP 主数据/授权/
账号快照表，其余 41 张原表不变，最终 `alembic check` 无 schema 漂移。

生产结果：旧 ERP 已停写并生成最终一致性备份；`data_handle` 已从 0034 升级到 0037，
12 张业务历史表共导入 3,950 行，硬关联孤儿为 0，12 个 sequence 已同步。生产应用、
统一身份/账号适配器和高保真页面均已发布；旧 `erp.aiggtj.com` 的 GET/HEAD 入口通过
无缓存 302 切换到新系统，非读取请求返回 405。浏览器验收确认兑换码页包含 19 个任务组、
27 个批次和 450/450 的已导入任务，审计权限、统一远端账号和旧路径兼容均正常。

旧数据库、应用镜像、最终备份与回退负责人仍保留；回退只需移除独立入口重定向并启动旧
API/Web/edge-proxy，不对 `data_handle` 执行降级。远端连接检测、标签同步、兑换码远端
创建/发布/取消/下载仍为“执行禁用”，本次切换没有调用任何远端业务接口。

## 4. 迁移期间的状态规则

只允许使用以下状态：

- `未开始`：尚未导入或实现。
- `已导入/未接入`：源码存在，但未使用统一身份、数据和路由。
- `部分等价`：主流程存在，但页面/API/权限/导出仍有差异。
- `执行禁用`：远端协议代码存在，但生产无入口。
- `功能等价`：逐项差异测试通过。
- `生产切换`：数据迁移和生产验收完成。

不得把“测试文件存在”“状态机存在”或“服务健康”写成 ERP 完整迁移完成。

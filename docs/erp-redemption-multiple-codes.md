# 每组兑换码数量

当前项目 `/erp/redemption` 的“每组兑换码数量（邀请码数量）”对应远端 `key_number`，默认 1，可填写 1–1000 的整数。1000 是本项目的输入上限，不表示已验证的远端上限。该参数与“单兑换码领取次数”独立。

每个盘口仍按“开始兑换日 × 用户类型/标签档位”创建一组远端配置。例：1 个盘口、7 天、5 档、每组 5 个码，共 35 组配置、175 个独立兑换码。不会把 5 个码拆成 5 组，也不会改变日期、生效时间、标签或领取次数。

## 保存与导出

- 新表 `erp_compat_redemption_issue_codes` 保存一组内的全部号码；保留原 `redemption_code` 作为首码兼容字段。
- 下载走统一远端账号及 DOWNLOAD 能力校验。每组下载数量必须等于其创建时的数量；不足、重复、非法号码不能标记完成。
- 同组重复下载/导入是幂等的；禁止覆盖已有号码和跨组重复号码。
- 原 `expectedCodeCount`、`importedCount` 继续计配置组，避免改变已有状态机。新增 `plannedCodeCount`、`importedCodeCount` 计实际号码；明细提供 `redemptionCodes` 数组及兼容的换行文本。
- Excel 每个号码单独占一条码记录，保留原日期、档位布局；多盘口的 All 汇总页与各盘口页均导出全部号码。每组 1 个码的布局不变。

## 发布要求

应用发布前需要单独执行 Alembic `20260905_0040 → 20260905_0041`。本次代码实现不执行线上迁移或发布。

迁移新建号码明细表并回填历史首码，不删除旧字段；为批次数量增加 1–1000 校验。发布前需确认目标 `data_handle`、备份及执行窗口，停写兑换码业务以避免旧版本在迁移/发布间继续写入。仅通过仓库发布脚本执行。

产生多码批次后，不可回滚到只支持单码的应用或降级删明细表。迁移的 downgrade 会拒绝有多码数据的情况，应保留数据并向前修复；必要恢复备份需另行确认，不能静默丢弃额外号码。单码回退也应先检查迁移后是否出现需要保留的新写入。

## 本地验证

- Java HTTP 流程覆盖每组 1／5：创建参数、发布、数量不足、完整下载入库和重复导入。
- Python 统一账号适配器覆盖 1／5 个码，以及未确认请求不得访问远端、缺码、重复与非法号码。
- 迁移测试覆盖旧首码回填、多码唯一性、数量约束及禁止有损降级。
- Excel 测试覆盖日充值、近 7 天、多盘口汇总及各盘口页。
- 当前项目本地浏览器模拟接口检查：默认 1、改为 5，汇总从 35 个码变为 175 个码；未创建或发布远端任务。

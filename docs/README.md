## 1. 项目定位

Raj Data Handle 是一个独立的数据采集与分析系统。它通过 RajWin、RajLuck
远端管理后台 API 获取数据，统一沉淀、校验并形成分析指标，支持：

- RajWin 单平台分析；
- RajLuck 单平台分析；
- 两个平台的横向对比；
- 在币种、时区和指标口径一致时进行合并汇总；
- 渠道、支付、首充、LTV、留存等核心经营分析；
- 同步任务、数据质量和接口健康监控。

该系统不是复审系统的附属页面，也不通过 SSH 或直接读取复审数据库获取业务数据。
它应使用独立代码库、独立运行账号、独立数据库和独立部署流程。

## 3. 当前基线决策

下列决策可直接作为项目初始化约束：

| 编号 | 决策 |
|---|---|
| D-01 | 默认预设数据源 ID 为 `rajwin`、`rajluck`；管理员可新增使用相同只读 Connector 契约的盘口，来源 ID 创建后不可修改。 |
| D-02 | 所有事实、维度映射、同步任务、原始记录和权限都必须包含 `source_id`。 |
| D-03 | 两个平台的 UID、订单号、渠道码默认只在各自平台内唯一。 |
| D-04 | **已确认**：第一阶段只读，不包含远端管理、审核、订单修改，也不调用锁单、刷新订单、修改用户等远端写接口。 |
| D-05 | 前端查询本地分析库，不在用户请求链路中同步调用远端后台。 |
| D-06 | 使用独立分析数据库：RajLuck 生产目标固定为关联 RDS 中的 `data_handle`，账号采用已审批的独立数据库账号；禁止连接复审库 `review_recheck`。 |
| D-07 | 凭据、密码、TOTP Secret 和 JWT 不进入 Git，不在日志、接口响应或页面中展示。 |
| D-08 | MVP 使用 PostgreSQL；只有明细数据量被验证为超出容量后，再评估 ClickHouse。 |
| D-09 | 远端字段名不等于正式业务口径；LTV、留存、利润等指标必须经过业务验收。 |
| D-10 | RajWin 异常不得阻断 RajLuck，反之亦然。 |
| D-11 | **已确认**：首批业务模块比对支付平台订单与远端充值/提现订单，找出支付平台存在但远端遗漏或状态异常的订单并支持导出。 |
| D-12 | **已确认**：支付平台表格按平台维护版本化模板；支付平台时间列与远端时间列不写死，由用户校准并保存配置版本。 |
| D-13 | **已确认**：RajWin、RajLuck 运行同一套后台系统，接口路径、请求参数、响应结构和页面一致；代码共用一个 Connector，仅 base URL、凭据和业务数据不同。 |
| D-14 | **已确认**：支付明细上传后立即创建异步后台任务，按批次窗口拉取远端订单并保存到本地；用户可离开页面，完成后查看和导出结果。 |
| D-15 | **已确认**：支付平台成功、远端存在但状态非成功的订单必须标记为“远端状态异常”，在结果列表和导出中单独呈现。 |
| D-16 | **已确认**：所有登录用户拥有相同业务权限；角色差异只作用于系统设置，普通用户与管理员均可上传、校准、比对、查看和导出。 |
| D-17 | **已确认**：本地用户账号系统参照 `withdrawal_recheck_review` 的账号表、登录、验证码和用户管理流程，但使用本项目独立数据库，并补齐会话过期、共享限流和浏览器凭据安全。 |
| D-18 | **已确认**：部署时通过一次性命令创建首个管理员，之后由管理员在页面创建和维护其他用户。 |
| D-19 | **已确认**：用户上传的原始支付平台文件和系统生成的导出文件默认保留 3 天；管理员可在系统配置页修改默认值。 |
| D-20 | **已确认**：比对批次及结果记录默认保留 30 天；管理员可在系统配置页修改默认值。 |
| D-21 | **已确认**：从远端后台拉取并缓存在本地的充值、提现订单默认保留 30 天；管理员可在系统配置页修改默认值。 |
| D-22 | **已确认**：支付平台文件中的非成功订单也参与比对；结果列表、汇总和导出必须展示支付平台原始状态并支持筛选。 |
| D-23 | **已确认**：页面顶部“确认遗漏数”只统计支付平台成功状态且比对结果为确认遗漏的订单；其他状态仍保留在明细和分组中。 |
| D-24 | **已确认**：初始登记 `aelopay`、`elepay` 两个支付平台；平台、文件模板和远端渠道绑定分层建模，一个平台可有多个模板及多个支付渠道。 |
| D-25 | **已确认**：支持用户为当前批次配置表格列与远端标准字段的比对规则，管理员可将验证后的配置发布为全局模板版本。 |
| D-26 | **已确认**：`elePay(HX)` 代付文件在首批范围内，需要与远端提现订单执行遗漏和状态比对，而不只是登记模板。 |
| D-27 | **已确认**：比对批次的远端支付渠道由用户从当前来源和业务类型的远端字典中选择，模板不写死单一渠道。 |
| D-28 | **已确认**：管理员先在系统配置页维护内置或新增盘口的名称和 base URL，业务用户创建批次时再选择一个已启用来源。 |
| D-29 | **已确认**：远端登录账号、密码和 TOTP Secret 由管理员在盘口配置中维护；Secret 加密保存且永不回显，页面只展示配置状态，并提供服务端“测试连接”。 |
| D-30 | **已确认**：批量比对初次未找到的订单必须再按订单号调用远端接口精确复查；复查成功且仍不存在才能标记“确认遗漏”，复查失败或结果不确定时标记“待复查”。 |
| D-31 | **已确认**：支付文件中业务字段完全相同的重复行合并为一条比对结果，并保留重复次数和原始行号；同一订单号对应的金额、状态等关键字段不一致时标记“重复数据冲突”，不得自动判定遗漏。 |
| D-32 | **已确认**：相同文件和相同比对参数再次提交时提示已有批次并允许直接查看；用户可明确发起“重新比对”创建新执行版本，复用一份上传文件及导入快照，但强制刷新远端数据并保存独立结果。 |
| D-33 | **已确认**：业务批次和结果属于团队共享数据，不按创建人隔离；所有登录用户均可查看、重新比对和导出全部批次，页面展示创建人和操作记录，系统设置仍仅管理员可修改。 |
| D-34 | **已确认**：所有登录用户均可在二次确认后取消排队中或执行中的批次；系统协作式停止后保留进度和脱敏诊断，但取消批次不得发布确认遗漏结论，后续重新比对创建新执行版本。 |
| D-35 | **已确认**：盘口配置必须包含业务时区和币种，并在批次中保存快照；支付平台文件时间列的时区由用户在校准时独立确认，不能自动视为与盘口业务时区相同。 |
| D-36 | **已确认**：系统默认币种为印度卢比 `INR`；支付文件无币种列时由用户确认默认值，有明确异币种时仍按订单号比对但标记“金额未校验”，币种未知时禁止启动，MVP 不做汇率换算。 |
| D-37 | **已确认**：执行版本完成、失败、不完整或取消后，通过站内 `Alert` 通知该版本的创建人或重新比对发起人；其他用户不弹窗但仍可查看共享批次，MVP 不发送邮件或 Telegram。 |
| D-38 | **已确认**：默认业务导出为多工作表 Excel，包含汇总、确认遗漏、远端状态异常、待复查、重复数据冲突和全部明细；当前筛选结果可单独导出 CSV。 |
| D-39 | **已确认**：比对结果页面必须使用图表展示结果分布、状态交叉分布、时间趋势和渠道对比；图表与指标卡、明细表和导出使用同一筛选及统计口径。 |
| D-40 | **已确认**：共享批次列表的 MVP 图表只展示执行版本数量、状态、耗时和失败分类等运行信息，不跨批次汇总订单量、遗漏数或遗漏率；跨批次业务总览待去重口径明确后再增加。 |
| D-41 | **已确认**：RajWin、RajLuck 新建盘口配置时默认业务时区为印度标准时间 `Asia/Kolkata`（UTC+05:30）；管理员仍须确认并可分别修改。 |
| D-42 | **已确认**：提现订单页面改为查询本地 Excel 导出缓存；每日业务时区 `00:05:01` 自动导出前一天，手动刷新可选前天、昨天、今天。Excel 仅解析安全白名单，不保存银行卡、手机号、银行、IFSC、失败原因、IP 或原文件。 |
| D-43 | **已确认**：提现渠道汇总按盘口、创建日期和支付通道分组；成功金额仅汇总代付成功订单的到账金额，手续费仅汇总代付成功订单的提现手续费。 |

## 4. 建议技术栈

| 层 | 建议 |
|---|---|
| API | Python、FastAPI、Pydantic、SQLAlchemy |
| 采集 Worker | 独立 Python 进程、APScheduler、数据库任务锁 |
| 数据库 | PostgreSQL、Alembic、JSONB 原始层 + 标准化事实表 |
| 缓存与协调 | Redis |
| 前端 | Vue 3、TypeScript、Vite、Element Plus、ECharts |
| 部署 | Docker Compose、Nginx |
| 可观测性 | 结构化日志、Prometheus 指标、站内系统健康告警；外部告警通道后续评估 |

此选型用于降低与当前审核系统之间的认知成本，但新项目不应在运行时跨仓库导入审核系统业务代码。

## 5. 开发前必须确认

- RajWin、RajLuck 是否都能提供专用只读分析账号；
- 两个平台的实际业务时区和币种（界面默认 `Asia/Kolkata`、`INR`，仍需管理员确认）；
- 远端历史数据可查询范围、最大分页、并发和限流；
- 首批正式指标定义及负责人；
- 用户级敏感明细是否确有采集必要；
- 广告消耗继续人工录入，还是接入广告平台；
- 新系统的部署主机、域名、备份和告警渠道。

在上述问题未完全确认前，可以完成接口探测、双源采集框架和原始数据层，但不应把未经确认的指标公式标记为“正式口径”。

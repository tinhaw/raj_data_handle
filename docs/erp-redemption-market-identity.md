# 兑换码远端配置 ID 的盘口作用域与登记恢复

## 问题与首个断点

任务 #26 中，RajLuck 远端创建已返回成功，本地登记却命中了
`uq_erp_compat_redemption_issue_remote_configuration`。该约束原来仅使用
`remote_configuration_id`；其他盘口的同号记录被错误地视为重复。
这不是远端账号授权或 IP 白名单拒绝。

链路为：本地子任务 → 统一账号远端创建 → 成功回执 → **本地唯一约束失败**
→ 子任务失败。旧版本在最后一步丢失返回的配置 ID，直接重试可能重复创建。

## 修复与不变量

- 在子任务保存 `remote_market_id` 盘口快照，使用统一 `source` 数字映射，
  不新增账号、凭据或会话体系。
- 唯一键改为 `(remote_market_id, remote_configuration_id)`；不同盘口允许同号，
  同一盘口的不同账号不能重复登记同一配置。
- 市场值 0 仅保留给没有远端账号的历史人工/离线任务。真实远端调用必须解析实际盘口。
- 创建、登记、发布及下载校验任务盘口和当前账号盘口一致。账号变更不能悄悄改变历史归属。
- Java 收到创建成功结果后，若登记事务失败，另行持久化专用
  `remote_create_receipt_id`。点击重试只恢复本地登记，不重新调用远端创建。
  不从旧 `remote_reference_id` 或 SQL 文本推断成功回执。
- Python 统一执行器成功审计增加 `source_id` 和 `remote_configuration_id`，
  供跨服务登记失败时核对；不记录凭据或兑换码。
- 旧版本遗留的配置 ID 唯一冲突，在缺少可靠回执时拒绝盲目重建。

这不是覆盖所有网络中断场景的全链路 exactly-once 协议。
如果进程在远端成功后、接收/保存回执前中断，必须核对远端记录与审计，不能假定未创建。

## 迁移与发布边界

新增 Alembic `0043`，依赖尚未发布的预设迁移 `0042`。部署从已上线的
`0041` 顺序升级为 `0042 → 0043`，不得只发布 Java 包。
Flyway `V24` 仅供隔离的 standalone 测试，生产结构仍由 Alembic 管理。

迁移保留任务、配置 ID、兑换码和版本号，只增加盘口快照/回执字段并替换唯一约束。
若已有远端配置无法通过统一账号映射追溯盘口，迁移在 DDL 前终止，不能猜测归属。
存在跨盘口同号或尚未登记的成功回执时，拒绝降级；优先前向修复。

上线仍需通过本项目发布脚本，在已确认的窗口备份 `data_handle`、停止相关写入，
单独执行 schema-only，再发布兼容应用。不能运行旧版本应用写入新结构：旧代码不知道盘口作用域。
回退涉及备份时间点之后的数据损失风险，必须重新评估；不自动删数据来满足旧约束。

## 任务 #26 的后续恢复

本补丁不会重建或自动关联 #26 的远端配置，也不会自动发布任何兑换码。
部署后需在明确授权下只读核对 RajLuck 的既有配置：盘口、创建结果 ID、日期、
描述、用户类型/标签、奖励、数量及有效期必须逐项一致。
SQL 错误中的编号只能作为查询线索，不能作为直接回填依据。
确认后再单独恢复对应本地登记并刷新批次状态，不重新 POST 创建。

## 回归覆盖

- HTTP 统一执行器：跨盘口同号、同盘口跨账号冲突、数据库竞态兜底。
- 失败后保留回执、只重试本地登记、旧版本丢回执时拒绝重建。
- 人工登记仍按盘口判重，发布与下载不能跨盘口调用。
- SQLite / 独立 PostgreSQL：历史映射回填、兑换码保留、未知归属前置拦截、
  同盘口唯一性与跨盘口同号、安全降级保护。

本地 PostgreSQL 回归只接受 loopback 上的新建 `raj_scope_migration_test` 测试库，
通过 `RAJ_TEST_SCOPE_DATABASE_URL` 指定；严禁指向应用数据。

# Raj Data Handle 基础需求文档

> 文档状态：Draft v0.1
>
> 目标版本：MVP
>
> 日期：2026-07-24

## 1. 背景

当前复审系统已经具备调用远端管理后台的能力，并实现了部分经营统计页面。
但现状主要面向单个部署节点和复审业务，存在以下限制：

- 远端 base URL、凭据和 Token 以单一运行上下文为主，不适合作为集中式双数据源；
- 页面查询通常实时代理远端接口，受远端延迟、Token 和接口稳定性影响；
- 数据以快照和业务页面需求为中心，尚未形成统一的可追溯分析模型；
- RajWin、RajLuck 无统一来源维度、同步水位、质量检查和跨平台指标层；
- 分析能力与复审权限、数据库和部署生命周期耦合。

因此需要建设独立系统，统一采集 RajWin 与 RajLuck 的经营数据并提供稳定分析能力。

## 2. 产品目标

### 2.1 业务目标

1. 在一个系统内查看 RajWin、RajLuck 单独及对比数据。
2. 统一渠道、充值、提现、首充、LTV、留存等常用分析。
3. 将远端接口数据周期性沉淀到本地分析库，支持历史查询和重算。
4. 明确每个指标的来源、公式、时区、币种和最后更新时间。
5. 能发现接口故障、缺数、重复、口径偏差和异常波动。

### 2.2 技术目标

1. 每个数据源独立认证、独立 Token、独立限流、独立游标。
2. 采集任务可重试、可补数、可恢复，并且重复执行不产生重复数据。
3. 用户查询不依赖远端接口实时可用性。
4. 原始响应可追溯，标准化数据可查询，指标可复算。
5. 系统可先以模块化单体上线，并保留拆分 Worker 或引入 ClickHouse 的能力。

## 3. 非目标

> 业务确认（2026-07-24）：第一阶段不包含远端管理、审核或订单修改功能。

MVP 不包含：

- 远端订单审核、锁单、解锁、刷新、备注或用户资料修改；
- 替代现有初审或复审系统；
- 直接共享或写入 `review_recheck` 数据库；
- 任意 URL、任意接口路径的通用远端代理；
- 实时流计算或秒级大屏；
- 机器学习预测、自动经营决策；
- 未经确认的跨币种金额直接相加；
- 默认采集银行卡、手机号、完整 IP、设备指纹等敏感明细。

## 4. 用户与权限

| 角色 | 主要能力 |
|---|---|
| 普通用户 | 使用全部业务功能，包括上传文件、确认字段、校准时间、启动比对、查看结果和导出。 |
| 系统管理员 | 拥有全部业务能力，并可管理系统设置。 |

角色不限制业务操作，也不区分 RajWin、RajLuck 的查看和导出范围。只有系统设置需要
管理员权限，包括：

- RajWin、RajLuck 的 base URL、凭据引用、启停和请求限制；
- 用户账号和角色；
- 全局支付平台模板及 `pay_method` 默认映射的发布；
- Worker、存储、文件保留、告警等运行参数。

普通用户可以为当前批次确认或调整字段与时间映射；将映射发布为全局默认模板属于
系统设置。所有业务操作和系统设置仍记录操作者审计。

业务数据采用团队共享模型，不设置“仅创建人可见”：

- 所有有效登录用户可查看全部批次、结果、执行版本和业务操作记录；
- 所有有效登录用户可对任意批次发起重新比对、导出，并取消非终态批次；
- 批次列表支持按创建人筛选，但创建人不是访问控制条件；
- 批次活动记录对业务用户可见；用户管理、凭据和安全审计等系统信息仅管理员可见；
- 所有文件查看与下载仍必须经过登录校验，不提供匿名永久下载地址。

### 4.1 本地账号与登录

本地账号系统参照复审系统的使用方式，但不共享复审数据库或运行时会话。

| 编号 | 优先级 | 需求 |
|---|---:|---|
| FR-USER-01 | P0 | 使用独立本地用户表，字段至少包含用户名、密码哈希、显示名、角色、启用状态和创建/更新时间。 |
| FR-USER-02 | P0 | 角色简化为 `admin`、`user`；两者业务权限相同，只有 `admin` 可操作系统设置和用户管理。 |
| FR-USER-03 | P0 | 提供本地用户名、密码和图形验证码登录，登录接口执行跨进程共享的 IP/账号限流。 |
| FR-USER-04 | P0 | 密码只保存强哈希；登录失败统一返回错误，不泄露用户名是否存在。 |
| FR-USER-05 | P0 | 登录会话必须设置有效期；账号停用、密码重置和主动退出后，相应会话失效。 |
| FR-USER-06 | P0 | 前端不得在 LocalStorage、SessionStorage、IndexedDB 或 Cookie 中保存明文密码。 |
| FR-USER-07 | P0 | 管理员可创建、停用、启用用户及重置密码；禁止删除或停用最后一个有效管理员。 |
| FR-USER-08 | P0 | 登录成功、登录失败、退出、用户创建、状态修改、角色修改和密码重置均记录安全审计。 |
| FR-USER-09 | P0 | 部署时通过一次性引导命令创建首个管理员，后续用户仅由管理员在用户管理页面创建。 |
| FR-USER-10 | P0 | 引导命令通过安全交互、标准输入或受控 Secret 读取密码，不接受会暴露在进程列表或 Shell 历史中的明文密码参数。 |
| FR-USER-11 | P0 | 批次、结果和执行版本对所有有效登录用户共同可见，不按 `created_by` 做数据行级隔离。 |
| FR-USER-12 | P0 | 所有有效登录用户可查看、重新比对、导出任意业务批次，并取消排队中或执行中的批次；每次操作记录实际操作者和目标批次。 |
| FR-USER-13 | P0 | 批次活动记录可供所有业务用户查看；账号管理、远端凭据、系统配置和安全审计接口仍只允许管理员访问。 |

## 5. 核心使用场景

### 5.1 经营总览

用户选择日期、数据源和渠道后，查看：

- 注册人数、新增付费人数、充值金额、提现金额；
- 净入金、付费率、首充转化率、ARPU、ARPPU；
- RajWin 与 RajLuck 的趋势、占比和差异；
- 数据最后更新时间、是否完整及当前质量状态。

### 5.2 渠道分析

- 按日期、平台、渠道查看注册、首充、充值、提现、留存、LTV；
- 维护渠道别名和跨平台渠道映射；
- 录入或导入广告消耗；
- 计算注册成本、付费成本、ROAS、ROI；
- 展示渠道排行、趋势和异常波动；
- 对未知渠道、失效渠道和字典变化进行提示。

### 5.3 支付与资金分析

- 按支付渠道、渠道类型、金额区间分析充值和提现；
- 查看订单量、用户数、金额和成功率；手续费仅属于提现分析指标，不纳入充值汇总；
- 对比两个平台的同类支付通道；
- 识别成功率下降、金额突变、失败原因集中等问题；
- 支持远端汇总值与本地明细重算值对账。

### 5.4 首充、LTV 与留存

- 首充用户和次日复充率；
- D0、D1、D3、D7、D30 等 LTV；
- D1、D3、D7、D15、D30 等留存；
- 按来源、渠道和 Cohort 日期分析；
- 比率汇总必须按基数加权，禁止对百分比直接平均。

### 5.5 数据同步与质量

- 查看每个来源、每个数据集的最后成功时间；
- 查看同步耗时、页数、记录数、重试和失败原因；
- 手动触发指定来源、数据集、日期范围的补数；
- 检查缺失日期、重复记录、未知字典值和 Schema 漂移；
- 支持失败重跑，保留操作者、参数和结果审计。

## 6. MVP 功能需求

### 6.1 数据源管理

| 编号 | 优先级 | 需求 |
|---|---:|---|
| FR-SRC-01 | P0 | 系统默认预设 `rajwin`、`rajluck` 两个稳定的 `source_id`，并允许管理员新增使用相同 Connector 契约的盘口；`source_id` 创建后不可修改。 |
| FR-SRC-02 | P0 | 每个来源配置展示名、后台地址、业务时区、币种、启用状态和远端凭据状态。 |
| FR-SRC-03 | P0 | 数据源健康检查包含 DNS/TLS、登录、Token 探测和只读接口探测。 |
| FR-SRC-04 | P0 | 一个来源故障时，另一个来源可继续采集和查询。 |
| FR-SRC-05 | P1 | 展示最近一次成功、失败原因、连续失败次数和熔断状态。 |
| FR-SRC-06 | P0 | RajWin、RajLuck 共用同一套接口定义和 Connector 实现，通过来源配置注入 base URL、凭据及运行参数。 |
| FR-SRC-07 | P0 | 管理员在系统配置页维护每个来源的盘口显示名、base URL、启用状态和必要运行参数。 |
| FR-SRC-08 | P0 | 稳定 `source_id` 与可修改显示名分离；修改盘口名不改变历史数据归属。 |
| FR-SRC-09 | P0 | base URL 保存前必须规范化并执行 HTTPS、登录和只读端点健康检查，检查失败时不得静默启用。 |
| FR-SRC-10 | P0 | 业务页面只展示已启用来源；每个比对批次必须由用户选择且只能选择一个来源。 |
| FR-SRC-11 | P0 | 批次保存 `source_id`、盘口名和来源配置版本快照；后续修改显示名或 base URL 不改变历史批次。 |
| FR-SRC-12 | P0 | 管理员在盘口配置页录入或替换远端登录账号、密码和 TOTP Secret；读取接口只返回“是否已配置”、更新时间等元数据，任何 Secret 均不回显。 |
| FR-SRC-13 | P0 | 盘口配置提供服务端“测试连接”，依次验证 HTTPS、登录、TOTP、Token 和允许的只读端点，并返回分阶段的脱敏结果。 |
| FR-SRC-14 | P0 | 新盘口可先保存为停用草稿；启用或更换 base URL、账号、密码、TOTP Secret 后重新启用前，必须通过最近一次完整连接测试。 |
| FR-SRC-15 | P0 | 更新远端凭据后立即撤销该来源的缓存 Token；配置变更记录操作者、时间和字段名，但不记录旧值、新值或登录 payload。 |
| FR-SRC-16 | P0 | 业务时区和币种是盘口启用必填项；时区使用 IANA TZDB 标识，币种使用 ISO 4217 三字母代码。 |
| FR-SRC-17 | P0 | 保存盘口配置时校验时区和币种格式；缺失或无效时可保存为停用草稿，但不得启用或创建业务批次。 |
| FR-SRC-18 | P0 | 修改盘口业务时区或币种创建新的 `config_version`，不追溯改变历史批次和已标准化事实的口径。 |
| FR-SRC-19 | P0 | 新建盘口时币种字段默认预填 `INR`（印度卢比），管理员确认后保存，且仍可选择其他有效 ISO 4217 币种。 |
| FR-SRC-20 | P0 | 新建盘口时业务时区默认预填 `Asia/Kolkata`（印度标准时间，UTC+05:30），管理员确认后保存，且可选择其他有效 IANA 时区。 |
| FR-SRC-21 | P0 | 新增盘口必须先保存为停用草稿；来源 ID 为 2-64 位，以小写字母开头，仅包含小写字母、数字、下划线和连字符。 |
| FR-SRC-22 | P0 | 所有盘口（包括预设盘口）在停用且不存在历史比对批次时均可删除；删除同时清理本系统保存的加密凭据与渠道映射。 |
| FR-SRC-23 | P0 | 盘口连接测试成功后，按盘口同步两套只读字典：数据字典 `pay_channel` 的 `key/title` 保存为“支付渠道”（`key` 对应充值订单响应字段 `pay_method`），充值订单模块 `payChannel` 的 `value/label` 保存为“支付渠道名称”（`value` 对应响应字段 `pay_channel_name`）。数据字典页分别展示两套映射、来源、状态与最近同步时间；远端不再返回的条目标记为停用而不是物理删除。 |

### 6.2 远端认证与请求

| 编号 | 优先级 | 需求 |
|---|---:|---|
| FR-AUTH-01 | P0 | 支持用户名、密码、TOTP 登录并提取 JWT。 |
| FR-AUTH-02 | P0 | Token 必须按 `source_id + account_role` 隔离保存。 |
| FR-AUTH-03 | P0 | Token 即将过期或收到认证失败时，只允许一次单飞刷新。 |
| FR-AUTH-04 | P0 | 401、403、419、440 归类为认证失败，不进行无限重试。 |
| FR-AUTH-05 | P0 | 密码、TOTP、Token 不出现在日志、异常、任务参数和前端响应。 |
| FR-AUTH-06 | P0 | 远端用户名、密码和 TOTP Secret 使用部署在数据库之外的主密钥进行信封加密或由 Secret Manager 托管；数据库不得同时保存可直接解密它们的主密钥。 |
| FR-AUTH-07 | P0 | TOTP 一次性验证码仅在服务端内存中即时生成；连接测试结束后销毁测试会话，不把测试 Token 返回浏览器。 |
| FR-HTTP-01 | P0 | 支持超时、有限重试、指数退避、随机抖动和每来源限流。 |
| FR-HTTP-02 | P0 | 仅允许登记过的方法与路径；MVP 所有业务接口均为只读语义。 |
| FR-HTTP-03 | P1 | 保存脱敏请求摘要、响应状态、耗时和关联 `request_id`。 |

### 6.6 充值遗漏订单比对（首个业务模块）

> 业务确认（2026-07-24）：这是系统首个落地的业务分析模块。

| 编号 | 优先级 | 需求 |
|---|---:|---|
| FR-REC-01 | P0 | 用户先上传支付平台导出的充值/代收 Excel，再在解析前指定表头所在行（默认首行）；系统解析该行字段后，用户确认支付平台模板、来源、支付渠道和比较口径。 |
| FR-REC-02 | P0 | 系统校验文件结构，所有字段有效的支付平台订单均纳入比对，不因订单状态非成功而过滤。 |
| FR-REC-03 | P0 | 系统按 `source_id + pay_method + 时间窗口` 拉取远端充值订单，并遍历全部分页。 |
| FR-REC-04 | P0 | 解析后由用户确认表格列与远端订单字段的映射：默认以支付平台“商户订单号”与远端 `order_num` 比对，以“平台订单号”与远端 `out_trade_no` 交叉校验；确认结果随批次保存。 |
| FR-REC-05 | P0 | 金额不一致、订单号冲突、重复数据冲突和无效行不能直接归类为遗漏，必须单独展示。 |
| FR-REC-06 | P0 | 初次未匹配订单必须使用已配置的订单标识调用远端接口逐单精确复查；扩大时间窗口只能作为辅助措施，不能替代订单号精确复查。 |
| FR-REC-07 | P0 | 页面展示导入总数、纳入比较数、已匹配数、异常数、候选遗漏数和成功状态确认遗漏数。 |
| FR-REC-08 | P0 | 确认遗漏结果支持列表查询及 CSV/Excel 导出，导出至少包含两类订单号、金额、状态、关键时间、渠道和核验结果。 |

## 7. 首批页面

首个业务模块先交付：

1. 登录与个人信息；
2. 支付订单比对批次与文件上传；
3. 支付平台模板识别及字段映射；
4. 时间字段校准；
5. 代收/代付比对进度与结果；
6. 确认遗漏列表及导出；
7. 数据源、支付平台模板与渠道映射设置；
8. 同步任务、数据质量和审计日志。

经营总览、渠道、首充、LTV、留存等页面作为后续独立业务模块逐项增加。

## 8. 查询与展示规则

- 默认时间范围为最近 7 天，最大交互查询范围建议 366 天；
- 查询日期使用来源业务日，不以服务器本地日期替代；
- 数据库统一保存 UTC 时间，同时保存业务日期和来源时区；
- 金额展示必须带币种；币种不同不得默认合计；
- 比率需展示分子、分母或支持悬浮查看；
- 没有数据、数据为 0、尚未同步、同步失败必须区分；
- 汇总指标应提供“远端报表值”或“本地重算值”标签；
- 所有导出使用与页面相同的筛选和指标版本。

## 9. 初始同步频率建议

| 数据集 | 建议频率 | 回看窗口 |
|---|---:|---:|
| 当日经营/渠道日报 | 10–15 分钟 | 今天、昨天 |
| 支付渠道日报 | 10–15 分钟 | 今天、昨天 |
| 充值订单 Excel 缓存 | 每日业务时区的系统配置时间（默认 `00:00:01`） | 前一天完整自然日；可指定日期 |
| 提现订单 Excel 缓存 | 每日业务时区的系统配置时间（默认 `00:05:01`） | 前一天完整自然日；手动可选前天、昨天、今天 |
| 首充分析 | 30 分钟 | 最近 3 日 |
| LTV/留存 | 每日 3–4 次 | 最近 30–90 日滚动重算 |
| 字典 | 每日一次 | 全量覆盖 |
| 历史回填 | 低优先级 | 按日分片 |

这是初始值，联调时应根据远端限流、数据量和业务 SLA 调整。

充值、提现和转盘订单的自动同步失败后，按系统配置的次数与间隔重试；默认最多重试 3 次、间隔 5 分钟。首次自动同步不占用重试次数，设为 0 时不重试；手动刷新不受此限制。

## 10. 非功能需求

### 10.1 性能

- 31 天经营总览查询 P95 小于 2 秒；
- 366 天趋势查询 P95 小于 5 秒；
- 支持至少 20 个并发只读用户；
- 前端查询只访问本地 API 和缓存。

### 10.2 可用性

- 目标月可用性 99.5%；
- 关键日报新鲜度目标不超过 15 分钟；
- 单来源故障隔离；
- 同步任务支持重启恢复；
- 生产数据库具备每日备份和恢复演练。

### 10.3 安全

- 使用专用只读远端账号，不复用审核高权限账号；
- 远端动态凭据存 Secret Manager，或使用数据库外部署主密钥进行信封加密；
- 敏感字段默认脱敏；
- 导出、补数、配置修改和明文查看均写审计日志；
- TLS 证书必须验证；
- 禁止将远端 Token 返回给浏览器；
- 数据库账号和数据库与审核系统隔离。

### 10.4 可维护性

- 接口请求、解析、标准化、落库、指标计算分层；
- 每个接口有契约样例与单元测试；
- 指标定义具备版本号和负责人；
- Schema 漂移不得静默丢弃字段；
- 配置文件提供 example，真实地址和密钥不提交。

## 11. 验收标准

### 11.1 功能验收

- RajWin、RajLuck 均能独立登录、探测和同步；
- 一个来源停用或失败时，另一个来源正常工作；
- 所有核心页面可切换单平台和全部平台；
- 指定来源、数据集、日期范围可补数；
- 同一窗口重复执行三次，不产生重复业务记录；
- 页面与导出在相同筛选下结果一致；
- 普通用户可以使用全部业务功能，但不能修改系统设置。

### 11.2 数据验收

- 选取至少 3 个日期，逐项与两个远端后台核对；
- 核心人数、订单数应完全一致；
- 金额差异为 0，或在书面批准的舍入容差内；
- 跨午夜、月末和时区边界正确；
- 未知渠道、状态和字段不会静默丢失；
- LTV、留存、复充率至少提供一个可人工复算样例；
- 合并指标可下钻到 RajWin、RajLuck 原始贡献。

### 11.3 运维验收

- Token 失效可以单次自动刷新；
- 无法刷新时在 5 分钟内告警；
- 每次同步可追踪到请求、页数、落库量和错误；
- 完成单来源故障、任务重启和数据库恢复演练；
- 日志中不包含密码、TOTP、JWT 和未脱敏敏感字段。

## 12. MVP 里程碑

| 阶段 | 预计 | 主要交付物 |
|---|---:|---|
| M0 接口与口径确认 | 3–5 个工作日 | 双源能力矩阵、匿名响应样例、时区/币种/指标确认。 |
| M1 双源采集基础 | 1 周 | Source Registry、认证、Token、限流、原始层、任务中心。 |
| M2 标准化与质量 | 1–2 周 | 事实表、维度表、回填、对账、质量规则。 |
| M3 分析 MVP | 1–2 周 | 总览、整合、渠道、支付、首充、LTV、留存、导出。 |
| M4 上线加固 | 1 周 | RBAC、性能、告警、备份恢复、运维手册。 |

整体 MVP 预计 4–6 周，取决于远端历史数据范围和指标口径确认速度。

7. 用户和订单级敏感明细是否必须进入 MVP？

9. 新系统部署到独立主机还是临时共享基础设施？
